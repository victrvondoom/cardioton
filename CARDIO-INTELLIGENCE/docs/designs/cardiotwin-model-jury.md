## Problem Statement

CARDIO-INTELLIGENCE contains 31 absorbed projects. Today they reach the user as 31 cards in the
Intelligence Hub and 12 embedded apps, each with its own input form, its own state and its own idea of a
patient. The brief asks for one product: one patient, one data context, one pipeline, one digital twin.

About 20 of the 31 projects address the same clinical question from the same data: the probability of
overall coronary artery disease and of LAD, LCX and RCA stenosis, from the UCI Z-Alizadeh Sani 54-feature
clinical profile. **17 of those ship saved models** (57 `.joblib` and 10 `.pkl` files, counted from the hub
catalogue on 2026-10-13). Those 17 are the jury. The others have no saved model and are out of scope here.

## Demand Evidence

- No external users yet (stage: pre-product).
- The audience is a hackathon jury (Multimodal AI Hackathon 2026, Track A: Cardiovascular Risk
  Visualization & Prediction). That is demand for a convincing 5-minute end-to-end demo, not for a
  platform.
- Evidence still missing: any clinician or lab who would use this outside the contest.

## Status Quo

- What judges will compare against: single-team Track A entries, each with one model, one form and one 3D
  heart.
- Published work on Z-Alizadeh Sani mostly reports one optimised ensemble with high accuracy on the same
  303 patients:
  - hard-ensemble voting, PMC9783937
  - ensemble voting, arXiv 2210.14906
  - NE-nu-SVC, reporting 94.66% (ResearchGate 337370999)
- Inside this repo, the status quo is the hub: 31 cards plus iframes. It is accurate, but it reads as a
  directory, not a product.

## Target User & Narrowest Wedge

- **User:** a cardiologist deciding, for one patient with chest pain, whether to send them for invasive
  coronary angiography (the "cath" decision), and which vessel is most suspect. This is the demo persona.
  The output is research use only and is never a recommendation (see Constraints).
- **Wedge:** enter or select one patient once. All 17 jury models run on that record. One 3D heart shows,
  per vessel, what each model says and how much they disagree. The report is built from the same stored
  results.
- **Why this wedge:** single-model entries can't show it. Reviews of cardiovascular digital twins name
  verification, validation and uncertainty quantification as the basis of clinician trust ("Building Digital Twins for
  Cardiovascular Health", J Am Heart Assoc, doi:10.1161/JAHA.123.031981). Model disagreement is a visible, honest form of that
  uncertainty.

## Constraints

- **Research use only.** The jury view and the report carry a fixed label: "Research prototype. Not for
  clinical decision-making. Models trained on one 303-patient cohort without external validation." Each
  model's "decision" is that model's own threshold output, never a cath recommendation.
- **Credit.** Every project is the team's own work, and each original author's credit stays on their
  module and on any result their model produces.
- **No averaging.** Probabilities are never averaged or fused without a validated method. The models
  share training data, so agreement is not independent confirmation, and the UI says so.
- **No fabricated outputs.** Every non-result is shown as `blocked` with an exact reason.
- **Baseline stays green:** backend 1310 passed / 3 skipped, ruff clean, mypy 0 in 476 files, frontend
  352 tests, tsc 0, vite build.
- **No commits** without explicit authorization.

## Premises (agreed)

1. **One spine:** the per-patient cath decision (CAD + LAD/LCX/RCA on a 3D heart). The non-cardiac tools
   remain secondary tools: EpiCast, MedRelay billing, SafetyConnect, Memento, CaseTwin chest X-ray and
   MedScribe.
2. **One patient record for the jury:** the Z-Alizadeh Sani 54-feature schema, plus notes, ECG text and
   echo text. The 17 jury models read only this record. Secondary tools and cardiac projects without saved
   models keep their current inputs in this phase.
3. **One product startup:** models run under the main backend's control, with no per-project servers to
   start by hand. The execution model is under Components, item 3.
4. **No averaging:** each model's per-vessel output is shown together with the disagreement band,
   labelled "same training data, not independent validation".
5. **Intelligence Hub unchanged in this phase:** the hub and all 12 iframes stay where they are, and no
   iframe is retired in Approach A. Retiring them, and the parity test that would allow it, belongs to
   Approach B.

## Approaches Considered

### Approach A: Model Jury Twin (chosen)
- **What:** one patient record, an orchestrator over the 17 jury models, a per-vessel jury on the
  existing CardioTwin 3D heart, and an evidence report.
- **Effort:** depends on the spike table (see Assignment). Per-adapter costs:
  - loads cleanly with importable preprocessing: ~1 h CC
  - preprocessing must be re-implemented from a notebook and verified: ~half a day
  - needs a separate worker environment: ~half a day per environment

  Shared parts (record, orchestrator, store, view, report) are about 1 day CC.

### Approach B: Full fusion
- **What:** all seven product areas, native ports of all 12 apps with a parity test, a migration matrix
  and iframe retirement.
- **Not chosen now:** XL effort, with high risk of being half-built at demo time. It is the roadmap after
  A.

### Approach C: Disagreement-driven workup
- **What:** which missing measurement would most reduce disagreement, plus what-if flips.
- **Status:** a stretch goal after A.

## Recommended Approach: A, built so B's layers slot in later

### Architecture
```
Patient record (54 features + notes) -> Orchestrator -> one subprocess per jury member
        |                                    |                 \-> adapter: hash-checked model + project preprocessing
        v                                    v
Patient Workspace <- Jury view (3D heart) <- Results store (DB) -> Evidence report
```

### Components

1. **Patient record** (core backend, `app/cardiotwin/`)
   - One typed schema for the 54 features. Each feature carries a value, a unit, a source (`case`,
     `dataset_row:<n>`, `note:<id>` or `manual`) and a state (`present` or `missing`).
   - Dataset rows are offered for the demo and always labelled with their row number.

2. **Note proposals**
   - The existing whole-word clinical extractor turns a note into *proposals* for record fields. Each
     proposal is `pending`, `accepted` or `rejected`.
   - A proposal never overwrites a value already entered. When a note conflicts with a structured value,
     both are shown and only an explicit accept replaces the value.
   - Accepting a proposal counts as an input edit (see Staleness).

3. **Execution model**
   - **One subprocess per jury member per run.** It is short-lived and uses the core's Python, or a
     pinned environment if the spike requires one.
   - The orchestrator starts these processes itself (bounded parallelism, default 4) and talks to them
     over a pipe, never a network port, so there is still one product startup.
   - A timeout kills only that member's process. Its result is `blocked: timeout`, and no other member is
     affected.
   - **Import isolation:** each process puts only its own project's folder on `sys.path`, so modules
     with the same name in two projects (`utils`, `preprocess`) never collide. A test runs two
     projects with same-named modules and checks that each gets its own code.
   - The cost is about 1-2 s of process start per member per run, which is acceptable for a button press.

4. **Adapters and loading safety**
   - **Jury member** = one project × one target, using the model that the project's own inference code
     loads for that target. The manifest records which file that is. Alternative classifiers a project
     saved but does not use for inference are not jury members.
   - Contract methods: `model_id`, `targets`, `required_features`, `predict(record)`, and a `metadata`
     method.
   - `targets` is a subset of CAD, LAD, LCX and RCA.
   - The `metadata` method reports the source module, author, training split, threshold, output kind,
     reported metrics and model file.
   - Model files load only if they are listed in a checked-in manifest (`modules/<slug>` path +
     SHA-256). Anything unlisted or with a mismatched hash is refused and reported as `blocked: integrity`.
   - Project preprocessing is imported from the module folder in its worker. It is not copied into `app/`,
     so the core keeps its ruff and mypy scope. New adapter and orchestrator code inside `app/` must pass
     both.
   - **Missing values:**
     - If a field the model needs is missing, impute it only with the project's own saved imputer and
       list it as `imputed` in the view and the report.
     - With no imputer, the model is `blocked: missing <fields>`.
   - **Output kind:** each model reports `calibrated_probability`, `probability` (uncalibrated),
     `score` or `label_only`.
     - The threshold comes from the project's code or metadata, and is `unknown` if none exists. It is
       never invented.
     - Only `calibrated_probability` and `probability` enter the probability band. In the glyph,
       calibrated outputs are filled marks and uncalibrated outputs are hollow.
     - `score` outputs are listed separately with their own scale, outside the band.
     - `label_only` models enter only the vote tally.
   - **Vote tally:**
     - Each member with a known threshold casts its own decision: positive if at or above its own
       threshold. The tally is shown per vessel ("6 of 9 above their own threshold") and in the report.
     - Members with an `unknown` threshold show "no decision" and are excluded from the tally.
   - **Training split:** `train_rows`, `test_rows`, or `unknown`. It must describe the data the *saved
     file* was fit on, verified from the code that writes the file. A notebook's evaluation split does not
     count if the model was later refit on all rows. If unverified, the split is `unknown`.
     - A dataset row inside a model's training rows is labelled `in-sample`.
     - If the split is unknown, the row is labelled `in-sample status unknown`.

5. **Results store**
   - Lives in the core's existing database, with a migration that adds a `model_runs` table.
   - Each row holds:
     - patient and case id
     - model id
     - model version: SHA-256 of the model file plus the preprocessing source files
     - inputs hash: SHA-256 of the canonical JSON of the exact feature values and states the adapter used
     - output, kind, threshold, imputed fields, in-sample label, explanation, status, timestamps
   - Results are retained as long as the case.
   - Note text is not copied into the store, only the accepted feature values and their note id.

6. **Staleness and runs**
   - **A result is `stale` when** its inputs hash no longer matches the record ("inputs changed") or its
     model version no longer matches the manifest ("model updated"). Stale results stay visible, greyed
     out with the reason.
   - Results that finish against an outdated inputs hash are stored as stale on arrival.
   - Reports can't be generated while any shown result is stale or a run is in progress.
   - Re-runs are manual. The Run button is disabled while a run is in progress, and a second request for
     the same patient joins it. Edits are allowed during a run. Once it finishes, Run is enabled again to
     refresh the stale results.

7. **Jury view on the 3D heart**
   - **Decision: no central value is coloured or shown.** A median or mean colour would read as a fused
     estimate, which the no-averaging constraint forbids.
   - Each vessel carries a two-tone stripe along its length: one end is the band's lowest model
     probability, the other end its highest, both on the existing CardioTwin risk ramp. Narrow agreement
     looks uniform, and wide disagreement looks visibly split.
   - Next to the vessel: the min-max values, the vote tally and a count such as "9 members, 2 blocked".
   - With exactly one model, the band is drawn as a point and labelled "single model".
   - With zero models, the vessel is uncoloured and labelled "no model".
   - With every model blocked, the vessel is hatched and the blocked reasons are listed.
   - Overall CAD has no vessel, so it appears in a panel beside the heart with the same band glyph.
   - Clicking a vessel lists every model: output, kind, threshold, own decision, in-sample label, imputed
     fields and author.

8. **Explanations**
   - Shown only where a project ships a per-patient explainer, such as a saved SHAP explainer or a linear
     model's coefficients.
   - Computed in the worker at run time and stored with the result, so the report matches the view.
   - Projects that ship only global importance plots link to them as "global, not this patient".

9. **Evidence report:** rendered from stored results only. It includes the research-use label,
   provenance, imputed fields, in-sample labels and blocked models.

10. **Access**
    - Every endpoint goes through the case's existing authorization check.
    - Tests:
      - another organisation's user gets 404
      - results never cross patients

## Open Questions

- **Spike outcomes:** how many of the 17 load in the core's environment, and how many need a pinned
  worker or a re-implemented transform.
- **Training splits:** for projects whose split isn't recorded, can it be recovered from their code? If
  not, those projects' dataset-row results stay labelled `in-sample status unknown`.
- **Demo deadline:** the date for the Track A submission and demo video is not recorded here.

## Success Criteria

- **Real results:** pick one patient, then press Run. At least half of the jury models that the spike
  marks loadable return real outputs through the orchestrator, with no iframe. The target is all of
  them, and the bar is fixed once the spike table exists.
- **Consistency:** the view and the report show identical stored values.
- **No silent gaps:** every non-result shows a specific `blocked:` reason, and every dataset-row result
  shows its in-sample label.
- **Baseline green**, plus new tests for:
  - adapter contract
  - integrity refusal
  - blocked and missing-value policy
  - in-sample labelling
  - staleness and the report block (input edits, model-version changes, results arriving after an edit)
  - import isolation between projects with same-named modules
  - timeout of one member not affecting the others
  - band, vote tally and no-decision handling
  - authorization
  - no cross-patient mixing
- **Recorded browser run:** patient, then jury, then report.

## Dependencies

- Each project's saved models, preprocessing code and dependency pins.
- The existing CardioTwin 3D heart and its vessel mapping (`/cardiotwin` route).
- The core's cases, database migrations and authorization.

## The Assignment

Run the loadability spike before writing any adapter. Time-box it to two hours, and mark each project as
`attempted` or `not attempted`. For each of the 17 jury projects:
1. In a throwaway process using the core backend's environment, load its model file. Use only the
   team's own files, and record each file's SHA-256 for the manifest.
2. Predict on one dataset row with the project's own preprocessing.
3. Record:
   - status: `loads`, `version error` or `missing preprocessing`
   - output kind
   - threshold source
   - training split known (yes or no): yes only if the code that *writes the saved file* shows which
     rows it was fit on
   - which file the project's own inference code loads per target (the jury member)

The table sets the effort estimate, the worker count and the success bar.

## What I noticed about how you think

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — consistency

**Problem**

> Components 3 runs one worker subprocess per Python environment, so most models share the core-environment worker. It also says a timeout kills the worker process and that 'a model that hangs or crashes affects only its own result'. Killing a shared worker also kills every other model running in that worker, so the isolation claim does not hold as designed.

**Remedy**

> Choose one: run each adapter call in its own short-lived subprocess or a per-model worker, or keep per-environment workers and state that a kill fails or re-queues the co-resident in-flight models. Specify what status those models get, for example 'blocked: worker restarted' or an automatic retry.

### R2-2 — feasibility

**Problem**

> Persisting from R1-7. Preprocessing is imported from each module folder into a shared worker, but the document does not say how name collisions are avoided. Seventeen projects loaded into one interpreter are likely to share top-level module names such as preprocess, utils or config, and the second import silently gets the first project's code.

**Remedy**

> State the import isolation: load each project by its package path (modules.<slug>.*), use importlib with a per-project namespace, or give each project its own process. Add a test that two projects with same-named modules each get their own code.

### R2-3 — clarity

**Problem**

> The output kinds include `score` (not a probability), but the jury view colours each vessel by the 'median model probability' and draws a min-max probability band. The document defines label_only handling but not whether scores enter the median and band, or whether calibrated and uncalibrated probabilities are mixed in one band without distinction.

**Remedy**

> State that `score` outputs are excluded from the probability band and median and listed separately, or define a validated mapping. State whether calibrated and uncalibrated probabilities share one band, and if so mark them differently in the glyph.

### R2-4 — clarity

**Problem**

> Component 4 says label_only models 'count toward the vote tally', but no vote tally is defined anywhere in the jury view (Component 7) or the report. A model with an `unknown` threshold has no own decision, and its entry in the tally and in the per-vessel 'own decision' column is unspecified.

**Remedy**

> Define the vote tally: what counts as a positive vote, where it is displayed, and that models with an unknown threshold show 'no decision' and are excluded from the tally.

### R2-5 — consistency

**Problem**

> The vessel colour on the risk ramp is the median model probability. The No-averaging constraint forbids fusing probabilities without a validated method. A single vessel colour from a central-tendency statistic is what a viewer reads as the fused estimate, whatever the label says.

**Remedy**

> Justify why a median colour is not fusion under the constraint, or encode the vessel by the band itself (for example colour by max, or a two-tone min-max), with the median only as a marker. Record the decision explicitly.

### R2-6 — clarity

**Problem**

> The unit of a 'jury model' is undefined. 17 projects ship 67 files, which include per-vessel models, imputers, scalers and possibly several alternative classifiers per project (for example RF, SVM and XGB). Counts such as '9 models, 2 blocked', the success bar and the adapter contract (one model_id) depend on which file is the project's jury member.

**Remedy**

> Define the jury member as one adapter per project, or one per project per target, and state how the shipped classifier is chosen when a project ships several (for example the project's own reported final model, recorded in the manifest).

### R2-7 — completeness

**Problem**

> The training-split metadata (`train_rows` / `test_rows`) may come from a notebook's evaluation split, while the saved model file was refit on all 303 rows after cross-validation, which is common. In that case a row labelled out-of-sample is actually in-sample, which is the safety risk the labelling was meant to prevent.

**Remedy**

> Require the split to describe the data the saved model file was actually fit on, verified from the code that writes the file. If that cannot be established, the split is `unknown`. Add this check to the spike's 'training split known' column.

### R2-8 — clarity

**Problem**

> A second Run joins an in-progress run, but the document does not say what happens when inputs are edited while a run is in progress. The joined run uses the old inputs, so its results are stale on arrival. The document also does not say whether a report can be generated while a run is still in progress.

**Remedy**

> Specify that results completing against an outdated inputs hash are stored as stale. State whether Run is disabled or queued after an edit during a run, and that report generation is blocked while a run is in progress.

### R2-9 — completeness

**Problem**

> Staleness is triggered only by an inputs-hash mismatch. Results also store a model version (model file plus preprocessing hash), but the document does not say what happens to stored results when a manifest update or a preprocessing change alters the model version. Old results would then be shown and reported as current.

**Remedy**

> Mark results stale when their stored model version differs from the current manifest version, and include this case in the staleness test.

### R2-10 — clarity

**Problem**

> The coaching section says the jury works 'without discarding 17 working models'. The document has not yet run the loadability spike, and its own success bar allows that only about half may load, so 'working' is asserted before the evidence exists.

**Remedy**

> Rephrase it as '17 saved models' or 'up to 17 models, pending the spike' so the coaching observation matches the evidence.
